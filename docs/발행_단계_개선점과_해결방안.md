# 뉴스레터 에이전트 — "발행" 단계 개선점과 해결방안

**담당: 발행(섹션 10~11) · 작성일: 2026-09-15**

---

## 실제로 발견한 문제 3가지

오늘 실제로 발행한 세 회차(로컬 2회 · 자동 실행 1회)와, 그 과정에서 **네 번 실패한 워크플로 실행**을 보고 발견했습니다.

### 문제 1 — 발행분이 한 매체·한 축으로 쏠림

발행 기록(`by_source` · `by_group`)을 보면 두 회차 모두 **한 매체가 과반을 차지하고, 두 축 중 하나가 0건**이었습니다.

| 회차 | 발행 | 매체 분포 | 묶음 분포 |
|---|---|---|---|
| 1회차 | 2건 | **Designboom 2** | 공간 2 · **문화 0** |
| 2회차 | 3건 | **문화포털 전시 2** · IndieWire 1 | 문화 3 · **공간 0** |

2회차는 선별 단계 로그에 `쿼터: 문화 5/3 · 공간 0/2`로 찍혔습니다. 즉 **발행 전에 이미 배분이 깨져 있었는데 그대로 나갔습니다.**

### 문제 2 — 키를 잘못 등록해도 화면으로는 확인이 안 됨 (3회 연속)

GitHub Actions에 키를 옮기면서 **세 번 연속으로 다른 값**이 들어갔고, 매번 실행이 실패한 뒤에야 알았습니다.

```
1차  OPENAI_API_KEY       → 401 Incorrect API key: d1b59711**********c1bf
2차  DISCORD_WEBHOOK_URL  → MissingSchema: Invalid URL '***': No scheme supplied
3차  KCISA_SERVICE_KEY    → 403 SERVICE_KEY_IS_NOT_REGISTERED · 키 121자
```

GitHub은 시크릿 값을 `***`로 가리기 때문에 **무엇이 잘못 들어갔는지 설정 화면으로는 확인할 방법이 없습니다.** 3차의 "121자"는 웹훅 주소 길이와 정확히 같았습니다.

### 문제 3 — 실패 로그에 예외 타입만 남아 원인을 세 번 헛짚음

같은 소스의 같은 실패를 네 번에 걸쳐 다르게 진단했습니다.

```
1차  문화포털 전시(HTTPError)        → 아무 정보 없음
2차  문화포털 전시(ConnectTimeout)   → 네트워크 문제로 오판, 타임아웃을 늘림
3차  문화포털 전시(RuntimeError)     → 사유를 담았는데 로그가 버림
4차  period2 HTTP 403 · SERVICE_KEY_IS_NOT_REGISTERED_ERROR · 키 121자/일반형
```

원인은 **로그를 남기는 코드**에 있었습니다. 실패를 기록하긴 했는데 `type(exc).__name__`만 남기고 **예외 메시지를 통째로 버리고 있었습니다.**

## 왜 이런 일이 생기는가

수업에서 짚은 구조가 발행 단계에서 다르게 나타난 것입니다.

1. **쿼터·상한을 거는 자리와 결과가 정해지는 자리가 다르다.**
   묶음 쿼터는 선별(섹션 7)에 걸려 있는데, 그 뒤에 검수(섹션 9)가 건수를 **줄입니다.** 선별에서 `문화 3 · 공간 2`로 맞춰도 검수에서 두 건이 떨어지면 발행은 `공간 2 · 문화 0`이 됩니다. **보장은 앞에서 걸고, 실제 결과는 뒤에서 정해집니다.**

2. **매체 상한이 후보 단계에만 있다.**
   `per_source_max`는 수집 후보에 걸려 있어서 "한 매체가 후보를 독차지"하는 건 막지만, **발행분 기준 상한은 어디에도 없습니다.** 후보 6건 중 2건이 최종에 오르면 그대로 나갑니다.

3. **발행은 되돌릴 수 없는데, 무엇이 잘못됐는지 알려주는 건 로그뿐이다.**
   자동 실행은 사람이 화면을 보고 있지 않습니다(섹션 11 — *"자동화는 일을 보이지 않게 만든다"*). 로그가 진단이 되지 않으면 고칠 방법이 없습니다.

4. **비밀값은 가려지는 것이 설계다.**
   등록하면 다시 볼 수 없는 건 불편이 아니라 의도인데(섹션 11), 그래서 **잘못 넣었는지 확인할 방법도 함께 사라집니다.**

## 해결방안 (코드로 강제하기)

### 해결 1 — 쿼터·매체 상한을 발행 직전에 한 번 더 건다

검수 탈락을 예상해 **선별에서 여유분을 뽑고**, 발행 직전에 최종 5건을 확정합니다.

```yaml
# settings.yaml
target: 5
overselect: 8        # 검수에서 30~40%가 떨어지므로 넉넉히 뽑는다
max_per_source: 2    # 후보가 아니라 '발행분' 기준 매체 상한
```

```python
def pick_for_publish(verified):
    """검수를 통과한 것 중에서 실제로 내보낼 것을 고른다.
    선별에서 맞춰 놓아도 검수가 줄이면 배분이 깨지므로, 여기서 마지막으로 건다."""
    out, per_src, per_grp, dropped = [], {}, {}, []

    # 1차: 묶음 쿼터를 먼저 채운다  2차: 남은 자리를 순서대로 메운다
    for quota_phase in (True, False):
        for d in verified:
            if d in out or len(out) >= TARGET:
                continue
            g = d.get("group")
            if quota_phase and per_grp.get(g, 0) >= QUOTA.get(g, 0):
                continue
            if per_src.get(d["source"], 0) >= MAX_PER_SOURCE:
                dropped.append(f"{d['headline'][:30]} — 매체 상한({d['source']})")
                continue
            per_src[d["source"]] = per_src.get(d["source"], 0) + 1
            per_grp[g] = per_grp.get(g, 0) + 1
            out.append(d)
    return out, dropped
```

**치르는 값**: 취재·검수를 5건이 아니라 8건 돌리므로 **호출 비용이 약 1.6배**가 됩니다. 발행 품질과 맞바꾸는 선택이고, 지표(`verify_fail`)를 며칠 쌓아 실제 탈락률을 보고 `overselect` 값을 조정하면 됩니다.

### 해결 2 — 비밀값은 '값' 대신 '모양'을 로그에 남긴다

값은 절대 찍지 않고 **길이와 형태만** 남깁니다. 이 한 줄이 있었다면 위 세 번의 실수를 **실행 전에** 전부 잡았습니다.

```python
def key_shape(name):
    v = os.environ.get(name, "")
    if not v:
        return f"{name}=없음"
    kind = "URL형" if v.startswith("http") else "sk-형" if v.startswith("sk-") else "일반형"
    return f"{name}={len(v)}자/{kind}"

# run() 첫 줄에
log.append("   · 키: " + " · ".join(
    key_shape(k) for k in ("OPENAI_API_KEY", "DISCORD_WEBHOOK_URL", "KCISA_SERVICE_KEY")))
```

```
· 키: OPENAI_API_KEY=164자/sk-형 · DISCORD_WEBHOOK_URL=121자/URL형 · KCISA_SERVICE_KEY=64자/일반형
```

### 해결 3 — 실패 로그에 사유를 싣는다 *(적용 완료)*

```python
# 전
dead.append(f"{src.name}({type(exc).__name__})")
# 후
reason = str(exc).strip() or type(exc).__name__
dead.append(f"{src.name}: {reason[:130]}")
```

함께 예외 메시지에 **상태 코드 · API가 준 사유 · 키의 모양**을 담도록 고쳤습니다. 이 수정 직후 네 번째 실행에서 진짜 원인이 한 줄로 드러났습니다.

## 이미 적용해 효과를 확인한 장치

| 장치 | 확인된 결과 |
|---|---|
| 발행 성공 판정을 `2xx`로 | `204`를 정상으로 처리 — 실패로 오해해 재발송하는 일 없음 |
| 발행한 주소를 파일에 기록 | 다음 실행에서 `기발행 -4`로 자동 제외. **제외를 매체 상한보다 먼저** 적용해 빈자리를 다른 기사가 채움 |
| 연습 실행은 기록하지 않음 | 안 보낸 것이 "보냄"으로 남아 영영 발행되지 않는 사고를 막음 |
| 기본값을 "보내지 않음"으로 | 프롬프트를 고치며 여러 번 돌려도 채널에 시험 발행이 쌓이지 않음 |
| 0건인 날에도 한 줄 발송 | 침묵과 고장이 구분됨 |
| 실행 기록을 저장소에 되커밋 | 러너는 사라지지만 기록은 남아, **로컬에서 보낸 것도 자동 실행이 인식** |

## 팀 토론용 한 줄 요약

발행 단계는 "안전하게 내보낸다"는 목표는 달성했지만(되돌릴 수 없는 자리에 AI를 두지 않았고, 기본값을 안전한 쪽으로 잡았고, 중복 발송을 코드로 막음), **"고르게 내보낸다"는 목표는 지켜지지 않는다** — 쿼터와 매체 상한이 **선별 단계**에 걸려 있는데 그 뒤의 검수가 건수를 줄이기 때문에, 실제 발행분에서는 매체 쏠림과 묶음 0건이 두 회차 연속 관측됨. **선별에서 여유분을 뽑고 발행 직전에 쿼터·매체 상한을 다시 거는 후처리**를 추가하면 해결된다. 덧붙여, 자동 실행에서는 **로그가 곧 유일한 진단 수단**이므로 실패 사유와 비밀값의 '모양'을 반드시 남겨야 한다 — 이게 없어서 같은 오류의 원인을 세 번 헛짚었다.
